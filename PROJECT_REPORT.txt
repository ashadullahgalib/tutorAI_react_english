--------------------------------------------------------------------------------
1. WHAT THIS PROJECT IS
--------------------------------------------------------------------------------

TUTOR AI is a full-stack AI-powered study assistant for Bangladeshi SSC
(Secondary School Certificate) students in grades 9-10. Students can ask
questions about their textbooks, request exercise solutions, and upload photos
of problems. The AI answers strictly from the textbook content — it does not
answer from general knowledge.

Subjects supported (folder names under /books/):
  - ssc_physics
  - ssc_chemistry
  - ssc_biology
  - ssc_math
  - ssc_ict
  - ssc_science
  - ssc_english_1st
  - ssc_english_2nd
  - ssc_bangla_sahitto
  (any folder with both content.json and exercise.json is auto-discovered)

Tech stack:
  - Backend:  Python, FastAPI, Google Gemini (google-genai SDK), FAISS,
              sentence-transformers, SQLite (for cache), Redis (optional)
  - Frontend: React (Create React App), ReactMarkdown, KaTeX (for math)
  - Config:   YAML (config/config.yaml), .env for secrets

3. DATA FORMAT
--------------------------------------------------------------------------------

Each subject has two JSON files. Both are arrays of objects (or a dict whose
values are objects — the indexer normalises either format to a list).

content.json — one object per textbook chunk:
{
  "page":     6,
  "chapter":  "Chapter One",
  "topic":    "1.2 Physical Quantities",
  "subtopic": "1.2.1 Fundamental Quantities",
  "type":     "concept",
  "content":  "A physical quantity is anything that can be measured..."
}

exercise.json — one object per exercise chunk:
{
  "page":          33,
  "chapter":       "Chapter One",
  "topic":         "1.7 Error and Accuracy",
  "subtopic":      "1.6.3 Stop Watch",
  "type":          "exercise",
  "exercise_type": "mcq",   // "mcq" | "cq" | "short_answer"
  "content":       "1. Who gave the quantum theory first? a) Planck ..."
}

IMPORTANT: exercise.json contains only the questions — there are no answer keys.
The AI solves exercises by reading the theory from content.json.

4. CONFIGURATION (config/config.yaml)
--------------------------------------------------------------------------------

paths:
  books_dir: "${COACHING_DATA_DIR}/books"   # where subject folders live
  logs_dir:  "logs"

models:
  embedding: "all-MiniLM-L6-v2"   # sentence-transformers model for FAISS
  llm:       "gemini-2.5-flash"    # text chat model
  vision:    "gemini-2.5-flash"    # image + text model

retrieval:
  top_k:                8    # chunks retrieved for content/concept questions
  top_k_exercise:      12    # chunks retrieved for exercise questions
  chat_history_limit:  20    # max turns stored in SessionState
  chat_history_send_limit: 8 # max turns sent to Gemini in a single request

Environment variables (set in .env or shell):
  GEMINI_API_KEY   — required; Google Gemini API key
  API_SECRET_KEY   — required; Bearer token all frontend requests must send
  REDIS_URL        — optional; if set, sessions persist in Redis (else in-memory)
  LOG_LEVEL        — optional; default INFO (DEBUG shows more detail)
  COACHING_DATA_DIR — optional; overrides the books_dir base path

5. BACKEND — HOW A CHAT REQUEST FLOWS
--------------------------------------------------------------------------------

Step 1 — Frontend sends POST /chat (JSON) or POST /chat/image (multipart)

Step 2 — app.py: _run_chat()
  a. Validates the subject exists (get_subjects() scans /books/).
  b. Retrieves the SessionState for this session_id.
  c. Calls resolve_query() — if the message contains pronouns like "it" or
     "this", prepends the last known topic so the search query is specific.
  d. Calls detect_mode() — returns "exercise" if the message contains keywords
     like: solve, exercise, mcq, cq, practice, quiz, practice problem, etc.
     Otherwise returns "content".
  e. Calls extract_chapter() — looks for "chapter N" or "chapter <word>" and
     returns a chapter filter string (e.g. "chapter 3"), or None.
  f. Calls search() with the expanded query, mode, subject, chapter, and k.

Step 3 — retriever.py: search()
  Gets the subject's FAISS bundle (loads/builds if not already in memory).
  Encodes the query with the sentence-transformers embedding model.
  Normalises the embedding vector (L2 norm for cosine similarity via FAISS IP).

  If mode == "content":
    Searches content_index only. Returns top_k most similar content chunks.

  If mode == "exercise":
    Searches exercise_index → top_k exercise question chunks.
    ALSO searches content_index → top_k // 2 concept chunks.
    Returns both lists concatenated.
    (This is critical: exercise.json has no answers, so the content is needed
    for Gemini to actually solve the problems.)

  If a chapter filter is given:
    Fetches top_k * 15 candidates from FAISS, then filters to only those whose
    "chapter" field matches the requested chapter (normalised, digit→word).

Step 4 — responder.py: generate_answer()
  Checks the semantic cache first (skipped for image requests).
  Cache key format: "[subject][mode] original_query"
  (Subject+mode prefix prevents cross-subject cache pollution.)

  Selects system prompt:
    - image    → _SYSTEM_IMAGE
    - exercise → _SYSTEM_EXERCISE
    - content  → _SYSTEM_CONTENT
  All three system prompts instruct Gemini to answer ONLY from the CONTEXT block
  and never use outside knowledge.

  Builds the prompt string:
    [system prompt]
    Previous conversation: (last N turns from chat history)
    TEXTBOOK CONTEXT:
      Chapter: ...
      Topic: ...
      Subtopic: ...
      Type: ...
      Content: ...
      ---
      (repeated for each retrieved chunk)
    STUDENT QUESTION:
      [student's message]

  Calls Gemini via google-genai SDK:
    client.models.generate_content(model=llm_model, contents=prompt_text)
  For image requests, the base64-encoded image is passed alongside the text.

  Saves the answer to the semantic cache (text requests only).
  Updates SessionState chat history.
  Returns the answer string.

Step 5 — app.py returns ChatResponse:
  { "answer": "...", "mode": "content|exercise", "session_id": "..." }

Step 6 — Frontend renders the answer via ReactMarkdown + KaTeX.


--------------------------------------------------------------------------------
6. FAISS INDEXING (core/indexer.py)
--------------------------------------------------------------------------------

What it does:
  Converts content.json and exercise.json into searchable vector indices.

How it works:
  For each chunk, builds a text string:
    "Chapter: X\nTopic: Y\nSubtopic: Z\nType: concept\nContent: [text]"
  Encodes all strings with sentence-transformers (all-MiniLM-L6-v2).
  L2-normalises the embeddings.
  Builds a FAISS IndexFlatIP (inner product = cosine similarity after L2 norm).
  Separately for content chunks and exercise chunks.

Caching:
  Saves content.faiss, exercise.faiss, faiss_meta.json per subject folder.
  faiss_meta.json stores: all chunk text, embedding model name, schema version.
  On startup, checks if cache is fresh:
    - All three files must exist.
    - Cache files must be newer than content.json and exercise.json.
    - schema_version must match CACHE_SCHEMA_VERSION = 2.
    - embedding_model name must match config.
  If stale → rebuilds and overwrites the cache files.

get_subject_bundle(subject):
  Entry point used by retriever.py.
  Returns a dict:
    {
      "content_index":  <faiss.Index>,
      "exercise_index": <faiss.Index>,
      "content_meta":   [list of content dicts],
      "exercise_meta":  [list of exercise dicts],
    }

7. SESSION MANAGEMENT (core/session.py + core/session_store.py)
--------------------------------------------------------------------------------

SessionState fields:
  - chat_history:       list of {"role": "user"|"assistant", "content": "..."}
  - current_topic:      topic string from the last retrieved chunk (for context)
  - active_concept:     same as current_topic (used for pronoun resolution)
  - last_answer_entity: entity extracted from the last answer (future use)
  - current_subject:    the subject currently selected by the student

Storage:
  In-memory (default): plain Python dict keyed by session_id (UUID4).
  Redis (if REDIS_URL is set): serialises SessionState to JSON, TTL = 4 hours.

Session lifecycle:
  POST /session/new   → creates a new UUID4, stores empty SessionState
  POST /chat          → loads state, uses it, saves updated state
  DELETE /session/:id → resets state (clears history + fields)


--------------------------------------------------------------------------------
8. SEMANTIC CACHE (cache/semantic_cache.py)
--------------------------------------------------------------------------------

Purpose: Avoid calling Gemini for near-duplicate questions.

How it works:
  Uses sentence-transformers (all-MiniLM-L6-v2) to embed each question.
  Stores question text, answer text, and embedding in SQLite (cache/cache.db).
  On lookup: computes cosine similarity between incoming query and all stored
  embeddings. If best score >= 0.85 threshold, returns the cached answer.

Cache key format (after fix):
  "[ssc_physics][exercise] what is newton's first law"
  The subject+mode prefix ensures physics questions never return biology answers.

Note: Delete cache/cache.db to clear all cached answers (e.g. after data changes
or after the retrieval fix described in section 11).


--------------------------------------------------------------------------------
9. RATE LIMITING (api/app.py)
--------------------------------------------------------------------------------

Uses slowapi (wrapper around limits library). Falls back to a no-op if slowapi
is not installed.

Limits:
  POST /session/new   → 20 requests/minute per IP
  POST /chat          → 30 requests/minute per IP
  POST /chat/image    → 15 requests/minute per IP


--------------------------------------------------------------------------------
10. FRONTEND ARCHITECTURE
--------------------------------------------------------------------------------

App.js (root):
  - On mount: calls createSession() and getSubjects() in parallel.
  - State: sessionId, subjects[], selectedSubject, messages[], loading, error.
  - handleSend(): adds user message optimistically, calls sendTextMessage() or
    sendImageMessage(), appends assistant response.
  - handleClearChat(): calls DELETE /session/:id, resets messages to welcome.

api.js:
  - All requests include "Authorization: Bearer <API_KEY>" header.
  - API_URL defaults to http://localhost:8000 (override via REACT_APP_API_URL).
  - API_KEY from REACT_APP_API_KEY env var.

Message.js:
  - User messages: right-aligned, red bubble.
  - Assistant messages: left-aligned with avatar, mode badge (Concept/Exercise).
  - Renders Markdown with ReactMarkdown.
  - Renders LaTeX math with remark-math + rehype-katex + KaTeX CSS.

ChatInput.js:
  - Auto-resizing textarea (max height 160px).
  - Image attach: validates type (JPEG/PNG/WEBP/GIF) and size (max 10MB).
  - Enter to send, Shift+Enter for newline.
  - If only image attached (no text), sends default message:
    "Please read and solve the problem shown in this photo."

Sidebar.js:
  - Lists all subjects returned by GET /subjects.
  - Subject icons mapped by folder name.
  - "Clear Chat" button at bottom.
  - Shows session ID prefix (first 8 chars) for debugging.

11. KNOWN ISSUES AND FIXES APPLIED
--------------------------------------------------------------------------------

BUG 1 (FIXED): Exercise mode only retrieved from exercise.json
  Problem: When mode="exercise", only exercise_index was searched. exercise.json
  contains questions without answers/theory. Gemini had no textbook grounding
  and used its own general knowledge instead.
  Fix: retriever.py search() now retrieves from BOTH exercise_index (top_k
  chunks) AND content_index (top_k // 2 chunks) in exercise mode.

BUG 2 (FIXED): Semantic cache not namespaced by subject or mode
  Problem: Cache key was just the raw query string. A physics exercise question
  could return a cached answer from a similar-sounding biology content question.
  Fix: Cache key prefixed with "[subject][mode]" in responder.py.

DEBUGGING AID (ADDED): Full prompt logged to terminal
  responder.py logs the complete prompt sent to Gemini (including retrieved
  context) at INFO level before every Gemini call. Visible in terminal and
  in logs/tutor.log. Use LOG_LEVEL=DEBUG for even more detail.

12. API ENDPOINTS REFERENCE
--------------------------------------------------------------------------------

All endpoints (except GET /health) require:
  Header: Authorization: Bearer <API_SECRET_KEY>

GET  /health
  No auth required.
  Returns: { status, gemini, subjects_loaded, subjects[], model? }
  Also performs a live Gemini connectivity check.

POST /session/new
  Rate limit: 20/min
  Body: (none)
  Returns: { "session_id": "<uuid4>" }

GET  /subjects
  Returns: { "subjects": ["ssc_physics", "ssc_chemistry", ...] }

POST /chat
  Rate limit: 30/min
  Body (JSON): { "session_id": "...", "message": "...", "subject": "..." }
  Returns: { "answer": "...", "mode": "content|exercise", "session_id": "..." }

POST /chat/image
  Rate limit: 15/min
  Body (multipart form):
    session_id: string
    message:    string (optional, defaults to "Please solve this problem...")
    subject:    string
    image:      file (JPEG/PNG/WEBP/GIF, max 10MB)
  Returns: { "answer": "...", "mode": "...", "session_id": "..." }

DELETE /session/{session_id}
  Clears chat history and context for the given session.
  Returns: { "status": "cleared" }

13. HOW TO RUN LOCALLY
--------------------------------------------------------------------------------

Backend:
  1. cd tutor_ai_react_gemini
  2. pip install fastapi uvicorn google-genai faiss-cpu sentence-transformers
     pyyaml python-dotenv slowapi redis
  3. Create .env:
       GEMINI_API_KEY=your_key_here
       API_SECRET_KEY=any_secret_string
  4. uvicorn api.app:app --reload --port 8000

Frontend:
  1. cd frontend
  2. npm install
  3. Create .env:
       REACT_APP_API_URL=http://localhost:8000
       REACT_APP_API_KEY=same_secret_string_as_backend
  4. npm start   (opens http://localhost:3000)

FAISS indices are built automatically on first request for each subject and
cached to disk. Subsequent startups load from cache unless the JSON files change.


--------------------------------------------------------------------------------
14. HOW TO ADD A NEW SUBJECT
--------------------------------------------------------------------------------

1. Create a folder: books/ssc_newsubject/
2. Add content.json — array of concept chunks (fields: page, chapter, topic,
   subtopic, type="concept", content).
3. Add exercise.json — array of exercise chunks (fields: page, chapter, topic,
   subtopic, type="exercise", exercise_type, content).
4. Restart the backend. The new subject is auto-discovered and indexed.
5. Add an icon in frontend/src/components/Sidebar.js SUBJECT_ICONS map.

15. COMPONENT DEPENDENCY MAP
--------------------------------------------------------------------------------

Request flow:

  [Browser]
     |
     | HTTP (fetch with Bearer token)
     v
  [api/app.py]  ← verifies token, rate-limits
     |
     ├── resolve_query()          [chat/retriever.py]  pronoun expansion
     ├── detect_mode()            [chat/responder.py]  content vs exercise
     ├── extract_chapter()        [chat/responder.py]  chapter filter
     ├── search()                 [chat/retriever.py]  FAISS lookup
     │     └── get_subject_bundle() [core/indexer.py]  load/build index
     │           └── load_subject() [core/indexer.py]  read JSON files
     ├── generate_answer()        [chat/responder.py]
     │     ├── get_cached_answer() [cache/semantic_cache.py]
     │     ├── _build_context()   [chat/responder.py]  format chunks
     │     ├── Gemini API call    [google-genai SDK]
     │     └── save_to_cache()    [cache/semantic_cache.py]
     └── session_set()            [core/session_store.py]  persist state
